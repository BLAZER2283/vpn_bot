# VPN-бот

Telegram-бот для продажи VPN-подписок. Одна подписка даёт доступ ко **всем**
серверам сразу: клиент получает одну ссылку, а какие за ней серверы — решает
база бота. Добавил сервер — он появился у всех, ключи никому не перевыдаются.

Ядро — панели [3x-ui](https://github.com/MHSanaei/3x-ui) на каждом сервере.
Бот ходит в их API, создаёт клиентов и агрегирует ссылки в свою подписку
(встроенный sub-сервер 3x-ui так не умеет — он знает только про свою панель).

## Что уже работает

- Пробные 2 дня, один раз на аккаунт
- Тарифы 1/3/6/12 месяцев; оплата звёздами Telegram или переводом с
  подтверждением админа
- Подписка одной ссылкой, до 6 устройств, безлимитный трафик
- Напоминания за 3 дня и за 1 день, автоотключение по истечении
- Сброс ссылки, если она утекла
- Админка: серверы, статистика, ручная выдача, рассылка

## Локальный запуск (без Docker и Postgres)

Нужен только Python 3.12+.

```bash
pip install -r requirements.txt

python run_local.py            # сквозной тест: БД, выдача, подписка, оплата
python run_local.py check      # быстрая проверка генератора ссылок
python run_local.py bot        # живой бот на SQLite
```

`python run_local.py` — главная команда. Она поднимает SQLite в файле,
заводит **фейковую** панель с двумя инбаундами, выдаёт триал, забирает
подписку HTTP-запросом и проверяет: продление не меняет ссылку, добавление
второго сервера тоже, повторный платёж не удваивает срок, истёкшая подписка
отдаёт 404. Ни Telegram, ни настоящий сервер для этого не нужны.

Для `run_local.py bot` нужен только `BOT_TOKEN` от @BotFather в `.env`.
Postgres не требуется — БД ляжет в `vpn_bot.db` рядом с проектом, схема
создастся сама. Серверов пока нет, поэтому подписка выдастся пустой; чтобы
она наполнилась, добавьте панель через `/addnode`.

Разница с продом ровно одна: там Postgres и схема через Alembic. Код
выбирает диалект сам по `DATABASE_URL`.

## Запуск в проде

```bash
cp .env.example .env
nano .env                  # BOT_TOKEN, ADMIN_IDS, пароль БД, SUB_BASE_URL
docker compose up -d --build
docker compose logs -f bot
```

Миграции применяются сами при старте (`entrypoint.sh`).

`SUB_BASE_URL` — адрес, по которому клиенты забирают подписку. Пока это
`http://ВАШ_IP:8080`; порт 8080 должен быть открыт.

## Проверка

Логика сборки ссылок проверяется без БД, сети и панели:

```bash
python -m scripts.selfcheck
```

Прогоняет разбор инбаунда и генерацию ссылки на зафиксированных примерах —
включая случаи, где старый скрипт ошибался (`pk` вместо `pbk`, `flow` на
WS-инбаунде, битый REALITY). Стоит запускать после правок
`app/panel/links.py`.

## Добавление сервера

Сначала посмотрите, что панель реально отдаёт (**только чтение**, ничего
не меняет):

```bash
docker compose run --rm bot python -m scripts.probe_panel \
    https://IP:PORT/secret_path admin password
```

Скрипт напечатает инбаунды с реальными `sni`, `pbk`, `sid` и соберёт ссылку
для уже существующего клиента. **Вставьте её в v2rayTun** — если работает,
генератор ссылок настроен верно.

Затем в боте:

```
/addnode Нидерланды|https://IP:PORT/secret|admin|pass|vpn.example.com|🇳🇱
```

Поля через `|` (в паролях панелей часто есть двоеточия и пробелы, а `|` —
почти никогда). Пятое поле — хост, который попадёт в ссылку.

Дальше бот сам прочитает инбаунды. Новая нода не назначается всем автоматически:
выдай её нужным подпискам командой `/grantnode`, затем прогоняй очередь через
`/drain`.

### Устройства и распределение нод

Каждое устройство получает отдельную ссылку и UUID. Лимит задаётся
`DEVICE_LIMIT` и по умолчанию равен 6:

```
/devices
/adddevice Телефон
/deldevice 2
```

Ноды назначаются подпискам индивидуально. Новая нода не раздаётся всем
автоматически: админ выдаёт её нужным пользователям:

```
/grantnode <tg_id> <node_id>
/revokenode <tg_id> <node_id>
```

После назначения запусти `/drain`. Один и тот же `/grantnode` можно повторить,
он не создаст дубликаты задач.

**Хост лучше домен, а не IP.** При смене адреса сервера ссылки с IP умрут
все разом, и придётся перевыдавать ключи всем — ровно то, чего вся эта
схема избегает.

## Админ-команды

| Команда | Что делает |
|---|---|
| `/stats` | пользователи, активные подписки, оплаты за 30 дней, зависшие выдачи |
| `/nodes` | серверы и их инбаунды, с причинами, если инбаунд исключён |
| `/addnode` | добавить сервер и раздать его всем активным подпискам |
| `/syncnodes` | перечитать инбаунды со всех панелей |
| `/drain` | прогнать очередь выдачи сейчас |
| `/give <tg_id> <m1\|7d>` | начислить вручную |
| `/whois <tg_id>` | что у пользователя, включая ошибки выдачи |
| `/say <текст>` | рассылка |

## Как устроено

```
app/
  panel/     клиент 3x-ui, разбор инбаундов, сборка vless-ссылок
  db/        модели и запросы
  services/  подписки, провиженинг, серверы, уведомления
  payments/  абстракция провайдеров + Stars + ручное подтверждение
  bot/       хендлеры, клавиатуры, тексты
  web/       subscription-endpoint
  scheduler/ фоновые задачи
```

### Почему выдача асинхронная

Оплата никогда не ждёт панель. Платёж и подписка фиксируются одной
транзакцией, клиенты на панелях ставятся в очередь
(`subscription_clients.state = pending`), воркер разгребает её с
экспоненциальным backoff.

Из этого следует главное: **деньги не теряются, даже если панель лежит.**
Подписка активна, ссылка валидна, серверы в неё дописываются по мере
готовности. Частичная выдача (2 сервера из 3) — нормальный режим, а не сбой;
бот так и пишет пользователю.

БД — источник истины. `subscription_clients` описывает, каким клиент должен
быть на панели; воркер добивается этого и только после **проверки чтением**
считает выдачу успешной. Проверка обязательна: `addClient` в 3x-ui умеет
вернуть пустой ответ, не создав клиента.

### Что было исправлено против старого скрипта

Прежний `add_client.py` работал, но содержал ошибки, которые на нескольких
серверах вылезли бы сразу:

- `POST /panel/api/inbounds/update/5` перезаписывает инбаунд целиком: две
  одновременные выдачи затирают друг друга. Заменено на точечные
  `addClient` / `updateClient`.
- В ссылке стоял `pk=`, канонический параметр REALITY — `pbk=`.
- `flow=xtls-rprx-vision` вешался на клиента всегда, хотя на WS-инбаунде он
  ломает соединение. Теперь ставится только для TCP.
- `sni`, `sid`, публичный ключ были захардкожены. Теперь читаются из панели,
  поэтому ротация ключей на сервере не убивает подписки.

### Тарифы

Правятся в `app/config.py`, `PLANS`. Цена — в звёздах. В БД пишется снимок
(`plan_code`, `months`, `amount`), так что изменение цены не переписывает
историю оплат.

### Подключить другую платёжку

`app/payments/base.py` — протокол на один метод. Добавьте файл рядом со
`stars.py` и вызовите `payments.service.credit()` при подтверждении платежа:
продление, идемпотентность и выдача уже общие.

Идемпотентность держится на уникальном `provider_payment_id`. Передавайте
идентификатор платежа провайдера — повторный вебхук просто не вставит
строку и ничего не начислит.

## Домен и HTTPS

Когда появится домен: раскомментируйте сервис `caddy` в
`docker-compose.yml`, задайте `SUB_DOMAIN` в `.env`, поменяйте
`SUB_BASE_URL` на `https://...`. Caddy сам выпустит сертификат, а `ports`
у бота можно убрать.

Учтите: если бот стоит на том же сервере, где REALITY занимает :443, Caddy
не получит этот порт и ACME не пройдёт. Варианты — отдельный дешёвый VPS
под бота (чище: упавшая нода не уносит продажи) либо DNS-01 challenge.

## Безопасность

- Креды панелей и токен бота — только в `.env`, он в `.gitignore`
- В панель кладётся `subId = s<id>`, не секретный токен подписки
- `sub_token` — 24 байта из `secrets`, rate-limit на эндпоинте, одинаковый
  404 для несуществующего и погашенного токена
- Postgres не публикует порт наружу
- В логи не пишутся URL панелей (там секретный путь)

Пароль панели и приватный ключ REALITY из старого `add_client.py` лежали
открытым текстом в OneDrive — **смените их**, прежде чем заводить эту панель
как ноду.
